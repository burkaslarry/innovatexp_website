Phased implementation plan

Phase 0 — Lock the baseline and offer definitions

Purpose: make subsequent changes reviewable without overwriting current work or publishing unintended prices.

  • Record the current diff, routes, metadata, EN/zh-hk desktop/mobile screenshots and existing booking/inquiry behavior. Preserve all five locale routes: en, zh-hk, zh-tw, ja and de.
  • Create an isolated implementation branch/worktree; verify Vercel project/branch mappings and preview environment separation before any push.
  • Approve the offer matrix above. Extend the existing catalog rather than creating unrelated pricing sources; distinguish fixed price, starting price and custom quote explicitly.
  • Record Stripe account readiness without handling bank credentials. A company-authorized person completes legal-entity verification and OCBC payout details in Stripe, and confirms account-specific capabilities.

Exit criteria: baseline and offer scope recorded, production controls understood, current prices unchanged unless explicitly approved. No production deployment.

Phase 1 — Improve conversion and product presentation

Purpose: clarify what customers receive and what they should do next before adding payment complexity.

  • Retain typography, colors, spacing, founder content, verified case studies, existing navigation and responsive layout. Add clearer offer copy and focused actions using current components.
  • Create a localized Snapshot detail page using the existing page shell: audience, one-workflow problem, included/excluded work, delivery trigger/timeline, customer inputs, revisions, price and upgrade terms. Keep the diagnosis CTA; purchase stays disabled until Phase 2 is ready.
  • Organize product presentation into entry, implementation and recurring services. Keep current inquiry-cart selections and existing anchors/URLs; correct placeholder and mixed-language pricing copy.
  • Bring AccountXP’s demo, before/after workflow, human review and pilot acceptance into the active product flow. Verify the available video’s content, rights, duration and performance before reuse; provide a text fallback.
  • Make System Care’s Technical Audit prerequisite visible and preserve response-versus-resolution boundaries. Do not offer unlimited changes or guarantee third-party repairs.
  • Align questionnaire options with the revised 3–60 audience and add region/timezone only after updating all locale strings. Keep Hong Kong SEO pages and positioning; add regional context selectively rather than replacing local content wholesale.
  • Fix retry/deduplication and booking slot/timezone integrity before paid fulfillment depends on booking. Establish provider-backed conversion events without exposing contact details.

Exit criteria: EN and Traditional Chinese have matching offer meaning and actions; other locales remain functional; mobile product discovery is clear; all existing booking, inquiry and SEO behavior passes regression review.

Phase 2 — Snapshot Payment Link pilot in test mode

Purpose: prove the purchase journey with one approved standard offer. Stripe Payment Links provide hosted checkout with a small integration surface.

  • Create a test-mode Snapshot product/price at the approved amount. Require product scope and policy acknowledgement, and keep quantity, optional extras and discounts fixed unless approved.
  • Add a configured purchase CTA, plus localized success/cancel guidance. A success URL is a navigation result, not payment proof.
  • For this pilot, an authorized operator verifies the completed payment in Stripe, including expected product, amount, currency and customer, before recording the order and inviting the buyer to paid intake or booking.
  • Use a private customer-specific invitation after verification. If a paid intake route is implemented now, enforce server-side authorization and an expiring order-bound token; do not use a public URL as the access check.
  • For Discovery, pilots and custom work, payment invitations follow a server-recorded qualification decision and agreed scope. Keep free diagnosis available independently.
  • Publish approved purchase/refund/cancellation and privacy disclosures with accessible links before checkout. Test receipt identity, return path, cancellation and operator reconciliation.

Exit criteria: test payment and cancellation work; unpaid visitors cannot enter paid fulfillment; the operator can reconcile and refund a test order. Live activation is a separate approval decision.

Phase 3 — Automate Checkout, verified orders and fulfillment

Purpose: replace manual reconciliation with reliable, traceable payment handling.

  • Add the Stripe server SDK and a server-side product-to-Price-ID allowlist. The browser submits an offer identifier, never the charge amount. Validate qualification where required, locale and allowed return URLs; make Checkout creation retry-safe.
  • Use raw request bytes and the endpoint signing secret to verify webhooks. Record each Stripe event ID once; tolerate retries and out-of-order delivery. Persist processing state before acknowledgement, and queue slow notifications. See Stripe’s webhook documentation.
  • Handle checkout completion, asynchronous payment success/failure and refund events for the enabled payment methods. Confirm actual paid status, expected item/currency/amount and test/live mode before granting fulfillment. Retrieve authoritative Stripe state when event ordering is ambiguous.
  • Use additive Neon migrations for orders, Stripe event receipts, notification/fulfillment work and hashed intake tokens. Store stable Stripe identifiers, offer/policy version, amount/currency, status, timestamps and limited attribution; do not store card data.
  • Separate payment state from delivery state. Prevent a delayed completion event from reopening a refunded order; handle partial refunds explicitly. Make access grants and emails idempotent across duplicate events and repeated success-page visits.
  • Protect order lookup, paid intake and future portal creation with customer/order authorization. Remove tokens and personal identifiers from logs and analytics. Reconcile missing webhook deliveries with a scheduled/operator-triggered repair procedure designed for the chosen hosting runtime.

Exit criteria: verified payment creates one order and one fulfillment grant; retries, notification failure, refunds and delayed events converge to correct state. Database or queue failure triggers retry rather than silent loss.

Phase 4 — Qualified recurring services and customer management

  • Add subscription checkout only for approved products and accepted System Care audits. Enforce eligibility server-side, even if someone reuses a shared checkout link.
  • Expose plan limits, setup fees, billing cadence, renewal/cancellation dates, support boundaries and the distinction between triage and repair before purchase.
  • Create an authorized customer portal; synchronize invoice payment/failure, cancellation and subscription changes. Define grace periods and service access rules before enforcing them.
  • Track qualified leads, proposals, won engagements and collected revenue separately. Keep recurring revenue separate from one-time setup and refunds. Custom projects retain quote, contract and milestone-payment handling.

Exit criteria: authorized customers can manage their own billing; wrong-customer access fails; renewal, failure and cancellation behavior match the approved service agreement.

Phase 5 — Preview verification, approval and controlled release

  • Run the checks below using test Stripe credentials, an isolated preview database and safe notification recipients. Verify no preview workflow sends live customer mail or mutates production data.
  • Complete public-claims checks, lint, TypeScript, meaningful payment/booking tests, build, dependency review and SEO/localized route checks. Review fixes individually; do not run the current predeploy:sraa shortcut blindly because it executes npm audit fix and changes dependencies.
  • Present the preview, final diff, offer/policy decisions, test results, migration plan, required environment names, Stripe Dashboard steps and rollback controls for production approval.
  • After explicit approval only, bind live resources, apply reviewed migrations and release. Reconcile a controlled live payment/refund and confirm notifications, access and SEO.

Rollback: disable new purchase CTAs first; revert presentation if needed. Preserve orders and event history, continue payment reconciliation and retain webhook compatibility for already-created checkouts. Do not drop tables or erase paid orders during rollback.
